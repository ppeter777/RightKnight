# ComplexityAssessment v1

Версия `complexity-diagnostic-v4` описывает исходную позицию и набор полученных
кандидатов. Это диагностический результат для проверки правил сложности на
партиях. Итогового балла «легко/сложно» ещё нет; `complexityFactor = 1.0`.

## Политика потерь

`LossPolicy.v2()` (`cp-loss-v2`) задаёт согласованные условные диапазоны:

| Потеря cp | LossCategory | Название | Приемлем |
| --- | --- | --- | --- |
| 0–19 | ACCURATE | Точный ход | Да |
| 20–49 | INACCURACY | Неточность | Да |
| 50–99 | MISTAKE | Ошибка | Нет |
| 100–199 | BLUNDER | Грубая ошибка | Нет |
| ≥200 | CRITICAL_BLUNDER | Критическая ошибка, зевок | Нет |
| Неизвестна | UNKNOWN | Недостаточно данных | Неизвестно |

Лучший ход и равноценные продолжения с нулевой потерей относятся к ACCURATE.
Оба диапазона ACCURATE и INACCURACY считаются приемлемыми. Порог
приемлемости включителен до 49 cp. Отрицательная потеря не допускается.

Политика используется и новым расчётом, и `MoveQualityClassifier` для уже
рассчитанного `lossCp` сыгранного хода. Старые enum-имена NEGLIGIBLE, SMALL,
SIGNIFICANT, SEVERE заменены: граница 20 cp отделяет точные ходы от неточностей, добавлена
граница 200 cp. В БД эти enum-категории не сохранялись; миграция не требуется.
Это изменение Java/JSON-контракта категории для потребителей классификатора.

Результат содержит версию и все четыре порога политики. Для эксперимента чистому
калькулятору можно явно передать другой `LossPolicy`; сервис чтения использует v2.
Другая политика должна иметь другое имя версии, чтобы результаты различались.

## Использование на существующем анализе

Внедрить `ComplexityAssessmentService` в потребителя:

```java
// id записи game_move_analysis, не id game_moves; срез первых пяти рангов.
ComplexityAssessment assessment = complexityAssessmentService.assess(analysisId, 5);
String json = objectMapper.writeValueAsString(assessment);
```

Сервис в read-only транзакции читает конкретную запись анализа, её корневой FEN,
MultiPV запуска и её кандидатов. Новый запуск Stockfish не нужен. Результат
вычисляется по запросу, отдельное поле БД и HTTP endpoint не добавлены. Его можно
сериализовать в JSON для выгрузки/проверки. Старые отсутствующие признаки остаются
неизвестными. Сервис не объединяет кандидатов разных запусков одной партии.

Чистый `ComplexityAssessmentCalculator.calculate(analysis, candidates,
fenBefore, requestedMultiPv, topPvLimit)` не обращается к БД и движку. FEN можно
передать null: тогда полнота набора неизвестна, а признаки новых нападений при
непустом списке целей без типа ходящей фигуры также могут остаться неизвестными.
Переданный FEN используется для проверки легальности кандидатов и полного
множества UCI, а также для определения типа ходящей фигуры после превращения.
Исходные entity/списки и доска партии не изменяются. При самостоятельном вызове
нужно передавать кандидатов именно данного корня; явно чужой parent ID отклоняется.

## Результат

- `position`: уже существующие признаки позиции из сохранённых метрик, включая
  unknownFeatures. Если метрики отсутствуют, они не заполняются скрытно из FEN.
- `requestedMultiPv`: запрошенное число; `analyzedCandidateCount`: фактическое.
- `candidateSetComplete`: множество UCI совпадает со всеми легальными ходами.
  При отсутствии FEN — null. Одинаковое количество само по себе не доказательство.
- `bestSecondGapCp`: разрыв первых двух рангов; отдельно `gapUnknownReasons`.
- `acceptableCandidateCount` / `acceptableCandidateRatio`: число и доля
  приемлемых среди всего полученного набора. При неизвестной оценке хотя бы
  одного кандидата оба null; знаменатель не уменьшается скрытно.
- `candidates`: отсортированные по рангу строки с UCI, исходной оценкой/глубиной,
  потерей относительно первого ранга, категорией потери, nullable acceptable,
  причинами неизвестности и пересекающимися категориями хода.
- `window`: срез рангов 1..topPvLimit, описанный ниже.
- `unknownReasons`: объединение причин неизвестности качества кандидатов;
  неизвестность геометрических признаков хранится отдельно в их классификации.

Сравниваются cp-оценки из одного анализа исходной позиции, с точки зрения стороны
очереди. Для каждого кандидата и первого ранга требуются `EXACT`, непустая cp-оценка,
отсутствие матовой оценки, положительная одинаковая фактическая depth. Мат не
переводится в условные cp. Rank 1 с неизвестной оценкой не получает искусственный
ноль потери. Ранжирование должно быть согласовано: обнаруженная инверсия оценок
делает качество набора неизвестным. Разрыв первых двух рассчитывается отдельно
и не зависит от неизвестности третьего. SelDepth — не критерий равенства depth.

Причины: NO_CANDIDATES, MISSING_RANK_ONE, MISSING_RANK_TWO, MISSING_CP_SCORE,
MATE_SCORE, NON_EXACT_SCORE, MISSING_DEPTH, DEPTH_MISMATCH, INCONSISTENT_RANKING.
Дубликаты рангов/UCI, незаконные ходы, несовместимый корень и противоречивые
метрики отклоняются как некорректные входные данные, а не принимаются за unknown.

## Признаки и качество в первых N вариантах

`topPvLimit` — настраиваемое окно наблюдения, не новая настройка движка.
Например, движок вернул MultiPV=5, а нас интересуют первые 3 варианта:

- `lossCategoryRanks`: ранги каждой категории потери, включая UNKNOWN;
- `moveCategoryRanks`: для каждого CAPTURE, RECAPTURE, OTHER_CAPTURE,
  GIVES_CHECK, PROMOTION, NEW_ATTACK_ON_MORE_VALUABLE_PIECE,
  NEW_PAWN_ATTACK_ON_PIECE — списки `presentRanks`, `unknownRanks`, `acceptableRanks`;
- `acceptableRanks` содержит только подтверждённые сочетания «признак есть и
  кандидат приемлем». Пустой список нельзя читать как отсутствие сочетания,
  если есть неизвестные признаки или качество кандидатов;
- `ranksComplete`: присутствуют все ранги до N; при известном числе легальных
  ходов L достаточно всех рангов до min(N,L). Дыры рангов не скрываются;
- `observedCandidateCount` и nullable `acceptableCandidateCount` относятся
  только к реально полученной части окна. Если ranksComplete=false, они не
  описывают полный топ-N.

Например, на ранее обсуждавшемся FEN тест использует **заданные тестом, не
результаты нового движкового анализа**, оценки 100, 90, 51, 50, −100:

| Ранг | Ход | Потеря | Категория | Приемлем |
| --- | --- | --- | --- | --- |
| 1 | Nfd4 | 0 | ACCURATE | Да |
| 2 | cxd4 | 10 | ACCURATE | Да |
| 3 | Bg5 | 49 | INACCURACY | Да |
| 4 | g4 | 50 | MISTAKE | Нет |
| 5 | Bxa6 | 200 | CRITICAL_BLUNDER | Нет |

Для топ-5 новое нападение на более ценную фигуру имеет presentRanks=[3,4],
acceptableRanks=[3]. Новое пешечное нападение имеет presentRanks=[4],
acceptableRanks=[]. Это позволяет проверять будущие правила сложности с
указанием конкретных ходов, а не объявлять любое нападение хорошим решением.

Все приемлемые кандидаты из ограниченного MultiPV не означают, что рассмотрены
все приемлемые ходы позиции. Один приемлемый среди рассмотренных не означает
«единственный хороший ход». SINGLE_LEGAL_MOVE определяется только полным числом
легальных ходов. Для пустого набора количество/доля приемлемых неизвестны даже
в терминальной позиции: следующего решения там нет.

## Границы первого этапа и проверка

Признаки ходов сейчас описывают корневой ход, а не события глубже в PV. Веса за
наличие шаха, взятия или нападения не назначены. Не используются сыгранный ход,
его lossCp, время решения и последующая оценка для определения сложности корня.
Графовые агрегаты словаря остаются следующим этапом; сами графы уже сохраняются.

Тесты проверяют диапазоны, неизвестные/матовые/ограниченные оценки, глубину,
полноту MultiPV и окна, ранги категорий, независимость от сыгранного хода,
чтение сохранённых кандидатов разных запусков и JSON round trip. Движок не
запускается. См. [словарь](analysis-dictionary.md) и
[описание формата кандидатов и графов](stage3-multipv.md).

## Объясняющие признаки (observed-patterns-v3)

`explanations` содержит восемь пересекающихся правил со статусами PRESENT / ABSENT / UNKNOWN:

- ALL_OBSERVED_CANDIDATES_ACCEPTABLE — все полученные кандидаты приемлемы.
- ONLY_ACCEPTABLE_OBSERVED_MOVE_IS_RECAPTURE — после взятия соперника единственный
  приемлемый среди рассмотренных ходов является ответным взятием.
- ONLY_ONE_ACCEPTABLE_OBSERVED_MOVE — среди рассмотренных ходов приемлем только
  один, независимо от активности, ответного взятия и абсолютной оценки.
- SINGLE_LEGAL_RECAPTURE_IS_ONLY_ACCEPTABLE_OBSERVED_MOVE — предыдущее правило
  об ответном взятии выполнено, и легальное ответное взятие в позиции только одно.
- MULTIPLE_LEGAL_RECAPTURES_ONLY_ONE_ACCEPTABLE_OBSERVED_MOVE — легальных ответных
  взятий несколько, все представлены среди кандидатов; приемлемо только одно
  из них, и других приемлемых ходов среди рассмотренных нет.
- MULTIPLE_ACCEPTABLE_OBSERVED_MOVES_ALL_RECAPTURES — приемлемых ходов среди
  рассмотренных несколько, и все они — ответные взятия. Может сочетаться с
  MULTIPLE_ACCEPTABLE_WITH_WORSE_ALTERNATIVES; уточняет характер выбора.
- MULTIPLE_ACCEPTABLE_WITH_WORSE_ALTERNATIVES — приемлемы как минимум два полученных
  кандидата, и есть хотя бы одна неприемлемая альтернатива.
- ONLY_ONE_ACTIVE_CONTINUATION_HAS_ADVANTAGE — активных кандидатов не менее двух,
  и только один из них достигает порога преимущества.

В observed-patterns-v3 имя TWO_OR_THREE_ACCEPTABLE_WITH_WORSE_ALTERNATIVES
заменено на MULTIPLE_ACCEPTABLE_WITH_WORSE_ALTERNATIVES. Это изменение имени
Java/JSON enum; потребителям нужно обновить фильтры по имени правила. Признаков
по-прежнему восемь. Верхняя граница числа приемлемых ходов удалена.
При PRESENT объяснение содержит фактические количества, например:
«Рассмотрено продолжений: 5; приемлемых: 4; за порогом приемлемости: 1».
При неизвестном качестве хотя бы одного кандидата правило остаётся UNKNOWN;
неизвестные оценки не учитываются как неприемлемые.

Правила относятся ко всему полученному MultiPV, независимо от topPvLimit.
Рядом сохраняются analyzedCandidateCount, candidateSetComplete, recaptureMovesCount
и ранги подтверждённых приемлемых, активных и активных с преимуществом ходов.
Для ответных взятий дополнительно возвращаются:

| Поле | Смысл |
| --- | --- |
| `recaptureRanks` | Ранги кандидатов с подтверждённым RECAPTURE |
| `acceptableRecaptureRanks` | Подтверждённые ответные взятия с acceptable=true |
| `unknownRecaptureRanks` | Ранги с неизвестным признаком RECAPTURE; это не список неизвестных оценок |
| `recapturesFullyAnalyzed` | Все легальные ответные взятия представлены в полученном наборе; качество проверяется отдельно |

`recapturesFullyAnalyzed` сравнивает количество подтверждённых ответных взятий
с `recaptureMovesCount`. При неизвестной предыстории, счётчике или признаке
RECAPTURE хотя бы одного кандидата возвращается null. Меньшее число означает
false; большее — противоречивые данные и ошибку входа. Кандидаты предварительно
проверяются на уникальность UCI. Этот показатель не равен candidateSetComplete:
все ответные взятия могут попасть в MultiPV, даже если другие легальные ходы не попали.

Неполный охват ответных взятий не позволяет подтвердить правило
MULTIPLE_LEGAL_RECAPTURES_ONLY_ONE_ACCEPTABLE_OBSERVED_MOVE: оно UNKNOWN,
если остальные условия выполнены. Качество нерассмотренного взятия не выводится
из его отсутствия в MultiPV. Общий признак ONLY_ACCEPTABLE_OBSERVED_MOVE_IS_RECAPTURE
при этом может быть PRESENT. Для нескольких приемлемых ответных взятий правило
явно ограничено наблюдаемым набором, а полнота приводится отдельно.

Неизвестность полноты не мешает описывать наблюдаемый набор, но запрещает вывод
«единственный во всей позиции». Все оценки должны быть сопоставимыми; при
неизвестном качестве набор не объявляется простым. Неполные списки подтверждённых
рангов не означают, что отсутствующие ранги имеют отрицательный признак.

Активность v1 — наличие хотя бы одного признака CAPTURE, GIVES_CHECK, PROMOTION,
NEW_ATTACK_ON_MORE_VALUABLE_PIECE или NEW_PAWN_ATTACK_ON_PIECE у корневого хода.
Если ни один не подтверждён, но хотя бы один неизвестен, активность неизвестна.
Тихие позиционные угрозы и активность глубже в PV этим определением не покрыты.
Нападение пешкой на пешку также не относится к NEW_PAWN_ATTACK_ON_PIECE.

Преимущество проверяется по абсолютной оценке с точки зрения стороны очереди:
`evalCp >= advantageThresholdCp`. Начальный экспериментальный порог +100 cp
явно записан в результате и настраивается:

```java
var assessment = complexityAssessmentService.assess(analysisId, 5, 100);
```

Этот порог не связан с потерей 49 cp: ход +99 после лучшего +100 приемлем,
но не достигает порога +100. Небольшое пересечение границы само по себе не
доказывает высокую сложность. Последнее правило считает только активные
продолжения; наличие тихого хода с преимуществом видно в общем списке кандидатов.

Правила — описания и гипотезы для человеческой проверки, не категории сложности.
Несколько способов ответного взятия могут требовать выбора; широкий приемлемый
набор не доказывает спокойствие позиции. Автоматические веса не назначаются.
Формат результата расширен до complexity-diagnostic-v4; политика потерь остаётся
cp-loss-v2. В БД результат по-прежнему не сохраняется, миграция не нужна.

### Примеры выбора ответного взятия и единственного приемлемого хода

Регрессионные проверки `RecaptureExplanationTest` используют следующие позиции:

| FEN | Ответные взятия на поле предыдущего взятия | Проверяемый случай |
| --- | --- | --- |
| `2r2rk1/pp2bppp/1q2p2n/3pP3/3P2P1/2B2N1P/PPRQbP2/2R3K1 w - - 0 20` | Qxe2 | Одно легальное ответное взятие, единственный приемлемый наблюдаемый ход |
| `5rk1/pp2b1pp/1qr1pP1n/3p4/3P2P1/1NB4P/PPR1QP2/2R3K1 b - - 0 23` | gxf6, Bxf6, Rxf6 | Три легальных ответных взятия, одно приемлемое; без оценки одного из трёх вывод неизвестен |
| `2r2rk1/pp1bbppp/1q2p2n/3pP3/3P2P1/2B2N1P/PPnQBP2/R1R3K1 w - - 0 18` | Qxc2, Rxc2 | Два приемлемых наблюдаемых хода, оба — ответные взятия |

Один FEN не доказывает, что предыдущий ход был взятием. Тесты задают легальные
иллюстративные предшествующие позиции и взятия, приводящие к этим FEN, и условные
сопоставимые оценки. Они проверяют расчёт, а не восстанавливают историю партии
или подтверждают качество ходов новым запуском Stockfish.

Для `r1bqkb1r/ppp1nppp/4p3/3pP3/1n1P4/5N2/PPP1BPPP/RNBQK2R b KQkq - 4 6`
оценка +0,60 в пользу белых записывается как −60 cp для чёрных, стороны очереди.
Если у …c5 оценка −60, а у остальных четырёх кандидатов −150, потери равны
0 и 90 cp: подтверждается ONLY_ONE_ACCEPTABLE_OBSERVED_MOVE. Преимущества чёрных
нет, поэтому ONLY_ONE_ACTIVE_CONTINUATION_HAS_ADVANTAGE отсутствует. Сам …c5
по текущему определению также не активный: он нападает пешкой на пешку d4.
Состав четырёх альтернатив в тесте условный, а не выгруженный MultiPV партии.
