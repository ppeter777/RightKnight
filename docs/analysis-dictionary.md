# Словарь анализа RightKnight

Редакция 0.10, 2026-11-10. Рабочий контракт для обсуждения и дальнейшей реализации.
Версия документа не является версией JSONB, миграции или модели сложности.

## 1. Термины

| Термин | Определение | Пример |
| --- | --- | --- |
| Позиция | Состояние доски с очередью хода и правами, необходимыми для генерации ходов | FEN перед ходом |
| Контекст партии | История, часы и параметры игроков, которых нет в самой позиции | Предыдущий ход, контроль времени |
| Данные позиции | Исходное описание фигур, связей и контроля | `pieces`, `relations`, `squareControl`, `xrayControl` |
| Метрика позиции | Числовая характеристика позиции с определёнными областью и способом расчёта | `legalMovesCount` |
| Признак позиции | Проверяемое логическое свойство; значение true, false или unknown | `IN_CHECK` |
| Событие хода | Конкретное изменение при переходе до → после, с участниками | Появилась связь нападения Лc8 → Фc6 |
| Признак хода | Логическое свойство хода, в том числе наличие события определённого вида | `GIVES_CHECK`, снятие последней защиты |
| Метрика хода | Числовая характеристика хода или перехода | Число добавленных связей нападения |
| Кандидат | Один допустимый корневой ход, рассмотренный движком; не вся PV | `b5c6` |
| PV | Продолжение, найденное движком для кандидата | Последовательность UCI-ходов |
| Приемлемый кандидат | Кандидат, удовлетворяющий явно выбранной политике качества | Отставание от лучшей найденной оценки не больше T cp |
| Оценка сложности | Интерпретация метрик и признаков относительно задачи и игрока | Сложность нахождения приемлемого хода |

Вход модели (*feature*) — общий технический термин: им может быть метрика,
логический признак или категория. В предметной документации эти понятия различаем.
Числовые оценки движка также называем метриками, но всегда указываем их источник:
они зависят от поиска, в отличие от полного числа легальных ходов.

`inCheck` исторически входит в Java-record `PositionMetrics`, хотя по этому
словарю это признак. Словарь не требует немедленного переименования классов.
Кандидат и сыгранный ход описываются одинаковыми правилами событий и признаков.

## 2. Общие соглашения

- Исходная позиция — перед рассматриваемым ходом. Для показателей обеих сторон
  явно передаём цвет `side`. Для метрики отдельной фигуры — `pieceId`.
- В подсчётах фигур ниже учитываем пешки, исключаем королей. Это явный контракт
  метрик, а не утверждение, что слово «фигура» всегда включает пешку.
- ID фигуры стабилен в пределах исходной позиции и её альтернатив. Он может
  совпадать с исходным полем, но не обозначает текущую координату. Между ходами
  партии такие ID без дополнительного сопоставления не сравниваем.
- Непосредственные нападения/защиты геометрические: связанная фигура тоже может
  давать связь. Это не доказательство легальности или выгодности взятия.
- X-ray учитывается отдельно. Сейчас это батарея через одну или две свои
  совместимые дальнобойные фигуры. Он не увеличивает число прямых атакующих.
- `0` означает рассчитанное отсутствие; `null`/unknown — отсутствие достаточных
  данных. Неподдержанная версия тоже не должна превращаться в ноль.
- Каждая метрика указывает единицу подсчёта: ходы, уникальные фигуры, связи,
  поля или цепочки. Пересекающиеся категории не суммируем как независимые.
- Сложность исходной позиции не зависит от фактически выбранного хода или
  потраченного на него времени. Эти данные нужны для последующего сравнения.

Статусы в таблицах: **есть** — реализован расчёт; **проект** — определение для
будущего расчёта, даже если все исходные данные уже сохраняются. Проектные имена
пока не являются полями Java или БД. Расчёт метрик кандидатов реализован в
[ComplexityAssessment v1](complexity-assessment.md); он выполняется по запросу, без сохранения агрегатов.

## 3. Метрики позиции из правил и контекста

Источник первых четырёх — `PositionMetricsCalculator`, полный набор легальных
ходов стороны очереди. Сохраняются в `game_move_analysis`.

| Имя | Определение и единица | Статус / неизвестно |
| --- | --- | --- |
| `legalMovesCount` | Число всех легальных ходов | Есть; null для нерассчитанных исторических записей |
| `captureMovesCount` | Число легальных взятий, включая en passant | Есть; null при отсутствии расчёта |
| `checkMovesCount` | Число легальных ходов, после которых соперник под шахом | Есть; null при отсутствии расчёта |
| `promotionMovesCount` | Число легальных ходов с превращением | Есть; null при отсутствии расчёта |
| `recaptureMovesCount` | Число легальных взятий фигуры, взявшей предыдущим ходом | Есть, `MoveContextCalculator`; null при неизвестной предыстории |

Четыре варианта превращения — четыре хода. Взятие с превращением и шахом входит
сразу в три счётчика. Ноль легальных ходов — терминальная позиция; ожидаемое
время следующего решения для неё не определяем. Ответное взятие требует истории:
после известного тихого хода соперника его число равно нулю. Для первого полухода
импортированной партии текущий код считает предыдущий ход отсутствующим.

## 4. Метрики позиции из геометрии связей

Все показатели раздела — **проект**. Источник — снимок графа одной позиции,
полный для требуемых видов связей. Неизвестный/неполный граф даёт null.
Для защиты используем семантику версии 2+: король может защищать другие фигуры,
но связи защиты самого короля не считаются. Старую семантику не меняем молча.

| Имя и область | Определение |
| --- | --- |
| `attackerCount(pieceId)` | Число уникальных вражеских источников прямых ATTACK к фигуре |
| `defenderCount(pieceId)` | Число уникальных своих источников DEFENCE к фигуре |
| `attackedPieceCount(side)` | Число уникальных фигур этого цвета с `attackerCount > 0` |
| `undefendedPieceCount(side)` | Число фигур этого цвета с `defenderCount == 0`, независимо от нападений |
| `attackedUndefendedPieceCount(side)` | Число фигур, одновременно атакованных и незащищённых |
| `controlledSquareCount(side)` | Число полей, непосредственно контролируемых хотя бы одной фигурой цвета; занятые поля включены |
| `contestedSquareCount` | Число полей, непосредственно контролируемых обоими цветами |
| `xrayControlCount(side)` | Число записей `(sourceId, square, throughIds)` с источником данного цвета; единица — цепочка к полю |

Последняя метрика неизвестна для старых снимков без x-ray. Она не является числом
уникальных батарей или полей: одна батарея может контролировать несколько полей.
Незащищённая фигура не обязательно уязвима, а атакованная незащищённая не
обязательно проигрывается. Название `hangingPieceCount` пока не вводим: оно
подразумевало бы более сильный тактический вывод. Разность ценностей фигур можно
вычислять из типов; наличие выгодного взятия из неё само по себе не следует.

## 5. Метрики набора кандидатов движка

Это характеристики анализа исходной позиции. Они зависят от MultiPV и поиска.
Не подмешиваем к ним оценку фактически сыгранного хода из отдельного анализа
позиции после хода. Каждый UCI-ход считается один раз.

| Имя | Определение | Статус |
| --- | --- | --- |
| `requestedMultiPv` | Запрошенное число вариантов | Есть как `GameAnalysisEntity.multiPv`; это параметр, не результат |
| `analyzedCandidateCount` | Число фактически полученных уникальных корневых кандидатов одного анализа | Есть, ComplexityAssessment |
| `bestSecondGapCp` | `evalCp(rank 1) - evalCp(rank 2)` | Есть; нужны две сопоставимые оценки |
| `acceptableCandidateCount` | Число полученных кандидатов, прошедших политику приемлемости | Есть; политика ниже |
| `acceptableCandidateRatio` | `acceptableCandidateCount / analyzedCandidateCount` | Есть; только доля внутри полученного набора; при нулевом знаменателе null |

### Политика приемлемости cp-loss-v2

Для первого эксперимента принят включительный порог T = 49 cp:
кандидат приемлем, если `bestEvalCp - candidateEvalCp <= T`. Диапазоны потери: 0–19 — точный ход, 20–49 — неточность,
50–99 — ошибка, 100–199 — грубая ошибка, от 200 — критическая ошибка.
Результат содержит версию политики и пороги; сравнивать
значения, полученные с разными порогами, как одну метрику нельзя.

Для расчёта количества/доли требуем непустой набор, первый ранг и сопоставимые
оценки всех полученных кандидатов: одна исходная позиция и запуск анализа,
единая перспектива стороны очереди, одинаковая фактическая глубина, `EXACT`,
числовые cp-оценки без матовых оценок. Оценки должны быть согласованы с ранжированием.
Если условие не выполнено, результат null с причиной; кандидатов с неизвестной
оценкой не исключаем скрытно из знаменателя. `EXACT` — тип результата поиска,
а не гарантия объективной оценки позиции. Для разрыва достаточно сопоставимости
первых двух кандидатов; неизвестная оценка третьего не мешает этому разрыву.

Смешение cp и матовых оценок пока не поддерживаем. Не заменяем мат условным
большим числом cp. Отдельная политика для матовых продолжений — дальнейший шаг.

### Полнота и интерпретация

Вместе с метриками рассматриваем признаки качества данных:

- `candidateSetComplete` (реализован): полученный набор UCI совпадает со всем набором
  легальных ходов. Совпадение только количества недостаточно.
- `ALL_OBSERVED_CANDIDATES_ACCEPTABLE` (реализован в объясняющих признаках): все полученные кандидаты приемлемы;
  unknown при пустом наборе или неизвестном результате политики.

При заданном MultiPV=5 и пяти приемлемых результатах вывод: «5 из 5 рассмотренных».
Если набор не полный, сколько ещё приемлемых ходов существует — неизвестно.
Даже результат «2 из 5» сам по себе не доказывает, что в позиции ровно два
приемлемых хода: это конечный поиск, а не полный точный перебор с доказательством.

Долю рассмотренных легальных ходов, если она понадобится, называем покрытием
набора, а не уверенностью оценки. `1.0` у acceptableCandidateRatio не означает
ни полное покрытие, ни низкую сложность позиции.

## 6. Метрики хода и события

Для сыгранного хода используем `played_attack_delta`, для кандидата —
`attack_delta`; корень у них общий. Дополнительные агрегаты ниже — **проект**.

| Метрика | Правило |
| --- | --- |
| `addedAttackRelationCount` | Число добавленных связей ATTACK обеих сторон; возможность фильтра по цвету источника |
| `removedAttackRelationCount` | Число снятых связей ATTACK обеих сторон; включает исчезновение связи из-за взятия цели/источника |
| `newlyAttackedPieceCount(side)` | Число сохранившихся фигур цвета: атакующих было 0, стало > 0 |
| `lostLastDefenderPieceCount(side)` | Число сохранившихся фигур цвета: защитников было > 0, стало 0 |

Для двух последних метрик восстанавливаем состояние после хода и сравниваем
счётчики по стабильным ID. Одна добавленная связь к уже атакованной фигуре не
увеличивает `newlyAttackedPieceCount`. Взятая фигура не считается «освободившейся
от нападения» или «потерявшей последнего защитника». Метрики неизвестны, если
нет подходящих снимка/дельты; сами по себе они не оценивают качество хода.

События прямых связей v1 доступны через Spring-сервис `directRelationEventService.assess(analysisId)`.
`analysisId` — ID строки `game_move_analysis`. Отчёт содержит `played` и список
`candidates` в порядке `pvRank`. Для каждого хода `targets` перечисляет изменившиеся
цели и взятые фигуры по стабильным ID. У цели есть состояние до и после хода и две
группы входящих связей, `attacks` и `defences`. В каждой группе указаны количества,
ушедшие участники в состоянии до хода и новые в состоянии после.

| Переход | Условие для группы связей цели |
| --- | --- |
| `FIRST_GAINED` | Появилась первая атака или защита, 0 → больше 0 |
| `LAST_LOST` | Исчезла последняя атака или защита сохранившейся фигуры |
| `REPLACED` | Число сохранилось, часть участников сменилась |
| `CHANGED` | Оба количества положительны и различаются |
| `UNCHANGED` | Состав группы сохранился. Пример — защита цели, получившей новое нападение |
| `TARGET_CAPTURED` | Входящие связи сняты из-за взятия цели. У самой цели `after == null` |

`AVAILABLE` с пустым списком целей означает, что сравнение выполнено. При отсутствии
снимка или дельты ход получает `MISSING_DATA`. При некорректном или несовпадающем UCI, разных или
неподдерживаемых версиях схемы — `INCOMPATIBLE_DATA`. Поддерживаются JSON v1–v3.
Состав слоёв прямых связей задаёт `calculatedKinds`; пропущенная группа имеет
значение null.

### Изменения прямого контроля полей

Для сыгранного хода и каждого MultiPV-кандидата `directRelationEventService.assess(analysisId)`
возвращает `squareControl.changes`. Запись появляется, когда хотя бы у одной стороны
изменился состав прямых контролирующих по стабильным ID и у поля есть хотя бы одна
причина для включения в отчёт. Поле встречается один раз, список `reasons` содержит
все применимые причины в порядке таблицы.

| Причина | Какие поля охватывает |
| --- | --- |
| `OCCUPANCY_CHANGED` | Поле заняли, освободили или на нём одну фигуру сменила другая |
| `CENTER` | d4, e4, d5, e5 |
| `WHITE_KING_ZONE` | Поля рядом с белым королём до или после хода |
| `BLACK_KING_ZONE` | Поля рядом с чёрным королём до или после хода |

Зона короля включает все соседние клетки в пределах доски. В графе они представлены
прямым геометрическим контролем короля независимо от легальности хода на клетку.
При ходе королём, включая рокировку, учитывается объединение старой и новой зон.
Если состав контролирующих у обеих сторон сохранился, запись для поля отсутствует.

| `occupancy` | `before` → `after` на поле |
| --- | --- |
| `OCCUPIED` | Пусто → фигура |
| `VACATED` | Фигура → пусто |
| `REPLACED` | Одна фигура → другая |
| `UNCHANGED` | Поле осталось пустым либо на нём осталась фигура с тем же ID |

В `before` и `after` указаны ID, цвет, тип и координата фигуры. Пустому полю
соответствует null. В `white` и `black` указаны `beforeCount`, `afterCount`,
участники `removed` в старом состоянии, `added` в новом и переход состава.
Для стороны, сохранившей состав контролирующих, переход равен `UNCHANGED`.

После `1.e4` из начальной позиции отчёт содержит пустое поле d5 с причиной
`CENTER` и `occupancy=UNCHANGED`. У белых прямой контроль меняется с 0 до 1:
добавляется пешка с ID e2 на поле e4. На самом e4 состав контролирующих сохранился.

Например, после `14.Rfc1` в позиции
`2r1kb1r/pp1b1ppp/1q2p3/3pPn2/1n1P4/N1B2N2/PP1QBPPP/R4RK1 w k - 7 14`
на f1 возникает `VACATED`. Прямой контроль белых остаётся 3 → 3 с переходом
`REPLACED`: уходит ладья a1, добавляется ладья с ID f1 на поле c1.
Если оба состава сохранились, смена занимающей фигуры сама по себе события не даёт.

Слой доступен на JSON v2 и v3. Пустой список со статусом `AVAILABLE` означает,
что подходящих событий нет. Для v1 или отсутствующего снимка/дельты статус
равен `MISSING_DATA`, для несовместимых входных данных — `INCOMPATIBLE_DATA`.

### Изменения батарей

Для сыгранного хода и каждого кандидата поле `batteries` содержит статус и список
`changes`. При JSON v3 исходные `xrayControl` и дельта хода дают отчёт
`AVAILABLE`, включая пустой список. При v1/v2 статус этого слоя — `MISSING_DATA`;
прямые события по-прежнему доступны. Несовместимость снимка и дельты даёт
`INCOMPATIBLE_DATA` обоим слоям.

Единица сравнения — фиксированное **поле, цвет батареи и направление от поля**.
Берём поля, занятые до или после хода, и поле назначения. Для него указываем
`MOVE_DESTINATION`, для остальных — `OCCUPIED_TARGET`. В `before` и `after`
есть цель (null для пустого поля), характер контроля и два списка:

- `directControllers` — все фигуры данного цвета, непосредственно контролирующие поле, со всех направлений. Их число равно длине списка.
- `battery` — фигуры только этого луча, от ближайшей к дальней. Первая непосредственно контролирует поле. `supportCount` — число остальных. При отсутствии батареи список пуст, одиночная прямая фигура остаётся в `directControllers`.

Схема v3 хранит до двух промежуточных фигур. Короткая цепочка и её продолжение
образуют одну батарею максимум из трёх фигур. Переходы сравнивают стабильные
ID и их порядок, поля и типы участников приводятся на соответствующий момент.

| Переход | Значение |
| --- | --- |
| `FORMED` / `DISSOLVED` | Батарея на луче появилась / исчезла |
| `COMPOSITION_CHANGED` | Изменилась длина, состав или порядок участников существующей батареи |
| `TARGET_CHANGED` | Батарея сохранилась, но поле заняла или покинула цель либо одна фигура сменила другую |

Например, слон f6 атакует белого слона d4, чёрный ферзь переходит с g8 на g7.
В отчёте для d4 появляется батарея чёрных на северо-восточном луче:
`directControllers` по-прежнему содержит слона f6, в `battery` после хода
стоят слон f6 и ферзь g7, поддержка меняется с 0 до 1. Если слон затем
сдвинется по этому же лучу с сохранением цели и порядка, события изменения
батареи на d4 не возникнет. Отчёт описывает геометрию. Для оценки размена требуется расчёт конкретного продолжения.

Событие содержит конкретных участников и переход. Признак «ход оставил фигуру
без защиты» означает наличие хотя бы одного соответствующего события; метрика
показывает число таких целей. Причину события (уход защитника, взятие, перекрытие)
пока не классифицируем. Вскрытые нападения уже отражаются в полном графе, но
отдельный семантический признак вскрытого нападения ещё требует правил.

## 7. Уже существующие признаки

| Признак | Смысл / источник |
| --- | --- |
| `IN_CHECK` | Король стороны очереди под шахом; `inCheck` |
| `SINGLE_LEGAL_MOVE` | `legalMovesCount == 1`; не «единственный хороший ход» |
| `PREVIOUS_MOVE_WAS_CAPTURE` | Предыдущий ход был взятием; контекст партии |
| `RECAPTURE_AVAILABLE` / `MULTIPLE_RECAPTURES_AVAILABLE` | `recaptureMovesCount > 0` / `> 1` |
| `OTHER_CAPTURE_AVAILABLE` | После взятия соперника доступно взятие другой цели |
| `CAPTURE`, `RECAPTURE`, `OTHER_CAPTURE` | Категории отдельного хода; OTHER_CAPTURE требует предыдущего взятия соперника и отсутствия ответного взятия этим ходом |
| `GIVES_CHECK`, `PROMOTION` | Ход даёт шах / превращает пешку |
| `NEW_ATTACK_ON_MORE_VALUABLE_PIECE` | Ходящая фигура создаёт прямое нападение на более ценную цель |
| `NEW_PAWN_ATTACK_ON_PIECE` | Ходящая пешка создаёт прямое нападение на непешечную цель |

Последние два признака вычисляет `MoveFeatureClassifier` из V16-списка новых
целей ходящей фигуры и её типа после хода. Это не все новые связи полного графа;
вскрытые нападения других фигур в эти два признака не входят. Категории могут
пересекаться, неизвестность не равна false. Полные контракты существующих
классификаторов описаны в документах, перечисленных ниже.

Объясняющие признаки набора кандидатов вычисляются в `ComplexityExplanations`
(`observed-patterns-v3`) и возвращаются в ComplexityAssessment без сохранения в БД.
Область — весь полученный MultiPV; статусы PRESENT / ABSENT / UNKNOWN:

| Признак | Условие |
| --- | --- |
| `ALL_OBSERVED_CANDIDATES_ACCEPTABLE` | Все рассмотренные кандидаты приемлемы |
| `ONLY_ONE_ACCEPTABLE_OBSERVED_MOVE` | Среди рассмотренных приемлем только один; активность и знак оценки не важны |
| `ONLY_ACCEPTABLE_OBSERVED_MOVE_IS_RECAPTURE` | Этот единственный приемлемый ход — ответное взятие |
| `SINGLE_LEGAL_RECAPTURE_IS_ONLY_ACCEPTABLE_OBSERVED_MOVE` | Предыдущее условие и ровно одно легальное ответное взятие |
| `MULTIPLE_LEGAL_RECAPTURES_ONLY_ONE_ACCEPTABLE_OBSERVED_MOVE` | Предыдущее общее условие об единственном приемлемом ответном взятии, несколько легальных ответных взятий, все они представлены среди кандидатов |
| `MULTIPLE_ACCEPTABLE_OBSERVED_MOVES_ALL_RECAPTURES` | Приемлемых рассмотренных ходов несколько, все — ответные взятия |
| `MULTIPLE_ACCEPTABLE_WITH_WORSE_ALTERNATIVES` | Приемлемы как минимум два рассмотренных хода, есть неприемлемые альтернативы |
| `ONLY_ONE_ACTIVE_CONTINUATION_HAS_ADVANTAGE` | Активных рассмотренных ходов ≥2, только один достигает advantageThresholdCp для стороны очереди |

Приемлемость определяется cp-loss-v2. Активность — хотя бы одно из CAPTURE,
GIVES_CHECK, PROMOTION, NEW_ATTACK_ON_MORE_VALUABLE_PIECE, NEW_PAWN_ATTACK_ON_PIECE.
Порог преимущества настраивается, по умолчанию +100 cp; отрицательная оценка
лучшего хода может дать единственный приемлемый ход, но не преимущество.
Неизвестные оценки/признаки дают UNKNOWN, если известные данные ещё не опровергли
условие. Неполный охват легальных ответных взятий запрещает вывод «из всех
ответных взятий приемлемо только одно». Признаки пересекаются; веса не назначены.

Подтверждающие данные: `recaptureMovesCount` (все легальные ответные взятия),
`recaptureRanks`, `acceptableRecaptureRanks`, `unknownRecaptureRanks` (неизвестен
сам признак RECAPTURE), nullable `recapturesFullyAnalyzed` (все легальные ответные
взятия представлены в анализе, независимо от известности качества). Примеры,
точные условия неизвестности и ограничения: [контракт результата](complexity-assessment.md).

## 8. Сложность, время и качество решения

В первом приближении целевая задача — **найти приемлемый ход**. Сложность нахождения
строго лучшего хода рассматриваем отдельно. Граница приемлемости и влияние уровня
игрока требуют проверки на позициях, а не назначения коэффициентов по названию
признака. Метрики движка помогают описать выбор, но не измеряют человеческую
трудность напрямую. Большой разрыв может соответствовать и очевидному взятию,
и труднонаходимому единственному спасению.

`expectedMoveTimeMs` — выход модели ожидаемого времени (`ExpectedMoveTimeCalculator`),
а не метрика доски. `complexityFactor` пока 1.0. Часы и давление времени относятся
к контексту решения; рейтинг и знакомство с мотивом — к контексту игрока.
Фактическое время, `lossCp` и отношение фактического времени к ожидаемому относятся
к результату сыгранного решения. Не используем их как входы сложности исходной
позиции. Нулевое lossCp для сыгранного первого кандидата в текущем коде — соглашение
оценки качества, не доказательство полной сопоставимости MultiPV.

## 9. Ведение словаря

Новый термин, метрика, признак или событие добавляется вместе с соответствующим PR.
Карточка включает: стабильное имя, русское определение, область (позиция/контекст/
ход/набор кандидатов), тип и единицу, источник, формулу или условие, параметры,
условия unknown, версию семантики, статус реализации, место хранения/расчёта,
пример и контрпример. Не вводим новый синоним для уже определённого понятия.

Изменение смысла требует записи в истории и решения о версии расчёта. Версии
JSON-структуры, извлечения геометрии, политики приемлемости и модели сложности
различаем. Документ с предложением не делает показатель реализованным.

Метрики набора кандидатов и контекст полноты реализованы в диагностической
версии ComplexityAssessment v1. Следующий этап — базовые агрегаты графа. До назначения весов — вывод значений и причин unknown
для проверки на реальных партиях. Сводный балл сложности этим документом не задан.
